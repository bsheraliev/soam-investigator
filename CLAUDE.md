# SOAM Investigator — инструкция для Claude Code

## Что строим
PWA для расследования авиационных событий по методологии SOAM (EUROCONTROL SOAM Quick Reference Guide V3, апрель 2023). Приложение ведёт расследователя по шагам и не даёт закрыть дело, пока не выполнены обязательные требования методологии.

Языки интерфейса: RU (основной), TJ, EN. Пользователь общается на русском — отвечай по-русски, коротко.

## Источник истины
- `docs/SOAM_QRG_V3.pdf` — методология. Термины, коды и контрольные вопросы брать только оттуда, не по памяти. Файл лежит только локально (в `.gitignore`): репозиторий публичный, перераспространять PDF EUROCONTROL нельзя. Нет файла — попросить владельца положить.
- `data/taxonomy.json` — единая таксономия; UI и логика читают её, а не хардкодят списки.
- Чего нет в QRG (нормы Приложения 13, национальные правила) — не выдумывать, помечать `TODO: сверить с первоисточником`.

## Стек и ограничения
- Vanilla JS (ES-модули), HTML, CSS. Без фреймворков, без сборщика, без npm-зависимостей в клиенте.
- Офлайн: service worker + IndexedDB. Все данные расследования хранятся локально.
- Хостинг: GitHub Pages. Сервера на этом этапе нет.
- При любом изменении кэшируемых файлов — поднять `CACHE_VERSION` в `sw.js`.
- Среда: Windows 11, PowerShell, git. Команды давать для PowerShell.
- Никаких внешних запросов с данными расследования (аналитика, CDN-шрифты, AI API) без явного разрешения пользователя.

## Модель данных (IndexedDB)
- `occurrence`: id, название, дата, место, тип, тяжесть (A, B, C, E, D), решение о расследовании, статус.
- `fact`: occurrenceId, текст, элемент SHEL/O (S, H, E, L, O), источник, вложения, `contributes` (результат теста вклада).
- `event`: occurrenceId, время, описание (хронология).
- `classification`: factId, элемент SOAM (HI, CC, OSF, BAR), подкатегория, состояние барьера (absent, failed, worked). Один факт может иметь несколько классификаций.
- `link`: fromId, toId (связи для SOAM Chart: OSF → CC → HI → BAR).
- `action`: occurrenceId, текст, адресует (список id барьеров и OSF), ответственный, срок, статус, отметки SMARTER.
- `qa`: occurrenceId, 12 пунктов чек-листа.

## Таксономия (data/taxonomy.json)
- Элементы SHEL/O с подсказками для сбора данных (QRG, стр. 12–15).
- Контекстные условия — 5 категорий: Workplace conditions, Organisational climate, Attitudes and personality factors, Human performance limitations, Physiological and emotional factors; примеры с пометкой error / common / non-compliance (стр. 23–27).
- OSF — 12 кодов: TR, WM, AC, CO, OC, CG, PP, MM, EI, RM, CM, EE; для каждого definition, issues, consequences (стр. 28–41).
- Барьеры — 6 типов: Awareness, Restriction, Detection, Control & Recovery, Protection & Containment, Escape & Rescue (стр. 42–44).
- Тест вклада и контрольные вопросы 1–4 (стр. 20–42).
- Чек-лист мер безопасности, SMARTER, QA-чек-лист (стр. 50–53).
- Каждая запись: `{ id, code, en, ru, tj }`. `en` — формулировка QRG. `ru` — перевод. `tj` — оставить пустым с `"tj_status": "todo"`, перевод проверит пользователь.

## Бизнес-правила (обязательные)
1. Факт попадает в анализ SOAM только после теста вклада; не прошедшие хранятся отдельно («прочие вопросы безопасности»).
2. При классификации показывать соответствующий контрольный вопрос и требовать подтверждения.
3. Human Involvement формулируется как действие/бездействие, без оценочных слов (Just Culture).
4. Каждый Absent/Failed Barrier и каждый OSF должен быть адресован минимум одной мерой. Иначе дело нельзя перевести в статус «Завершено».
5. Меры адресуют барьеры и OSF, а не людей.
6. Сработавшие барьеры (worked) фиксируются и выводятся в схеме отдельным цветом.
7. Отчёт формируется только после прохождения QA-чек-листа.

## Этапы
- Этап 0: каркас PWA, `taxonomy.json`, `db.js`, i18n, тестовые кейсы.
- Этап 1 (MVP): событие и тяжесть → факты SHEL/O → хронология → тест вклада и классификация.
- Этап 2: SOAM Chart (SVG, 4 колонки + исход, экспорт SVG/PNG), меры, QA-гейт.
- Этап 3: отчёт (печать в PDF из HTML, экспорт/импорт дела в JSON).
- Сервер, роли, AI-функции, PIRATe — позже, сейчас не делать и не закладывать лишнего.

## Как работать
- Перед началом этапа — короткий план (до 10 пунктов); подтверждения не ждать, сразу делать (решение владельца 2026-10-10).
- Интерфейс и новые строки — только русский; TJ и EN — после приёмки отделом расследований (решение владельца 2026-10-10).
- Маленькие шаги: один модуль — один коммит, сообщение коммита на русском.
- После каждого шага: что сделано, как проверить вручную (2–3 действия), что дальше.
- Не добавлять функции, которых нет в этапе. Идеи — в `docs/backlog.md`.
- Архитектурные решения — одной строкой в `docs/decisions.md` с датой.
- Тесты: чистая логика (правила 1, 4, 7; миграции БД) покрывается тестами в `tests/`, запускаемыми в браузере без зависимостей (`tests/index.html`).
- Проверка этапа: загрузить кейс из `data/cases/` и убедиться, что схема совпадает с QRG (стр. 47–49).

## Экономия лимитов
- По умолчанию модель Sonnet. Haiku — для переводов, заполнения JSON, мелких правок, поиска по коду (субагенты). Opus — только по явной просьбе пользователя или для разбора архитектурного тупика.
- Не перечитывать PDF целиком: читать только нужные страницы (номера указаны выше).
- Не переписывать файлы целиком ради мелкой правки — точечные изменения.
- Длинные сессии: после завершения этапа предложить `/clear`; состояние хранить в `docs/decisions.md` и `docs/backlog.md`, а не в контексте.

## Права и конфиденциальность
- QRG © EUROCONTROL: использование с указанием источника, некоммерческое, без изменения текста. В приложении — экран «О методологии» со ссылкой на источник. Английские формулировки не переписывать.
- Тестовые данные — только опубликованные кейсы из QRG. Реальные материалы расследований в репозиторий не коммитить (`.gitignore`: `data/private/`).
